# Hataori 3.0.4.0 MSI実機検証結果

## 実施日

2026-08-19

## 成果物

- MSI: `Hataori-3.0.4.0-x64.msi`
- SHA-256: `63181757E599941A222BF50D6E6FD17E6C2CD6954660F72C0BEB5521E5FBCF0F`
- WiX Toolset 5.0.2
- win-x64 self-contained single-file

## 変更内容

- `installer/Package.wxs`の`ServiceControl`へ`Start="install"`を追加。MSI Install／Major Upgrade直後にServiceが自動起動するようになった（従来は手動`Start-Service`が必要だった）。
- `ItogurumaClientOptionsValidator`／`Program.cs`を修正し、Itoguruma未連携（`hataori.service.json`未作成）でもHataori Server（Windows Service含む）が起動できるようにした。従来はToken未設定だけで起動時に例外が発生していた（`docs/adr/0015-itoguruma-optional-at-startup.md`）。
- `hataori doctor`の`itoguruma`チェックを、CLI側の独立再接続ではなく、稼働中のServerがControl Pipe経由で返す実際のItoguruma接続状態（`monitor`応答）を見るよう修正。CLIプロセスの実行アカウントにリンクされたTokenとService本体のToken状態が食い違う場合の誤報告を解消した。

## 合格

- `dotnet build` / `dotnet test`: 警告0、エラー0、全134件のテスト合格
- WiX ICE検証、警告0、エラー0でのMSIビルド
- 管理者権限での`msiexec /i`によるMajor Upgrade（`C:\Hataori`、3.0.3.0→3.0.4.0、Exit Code 0）
- Upgrade後、**手動`Start-Service`を実行せずに**Serviceが`Running`（`Start="install"`の効果を確認）
- Upgrade後の`hataori version` → `3.0.4.0`
- `hataori doctor` → `configuration`／`server`／`itoguruma`／`mcp`／`sqlite`／`claude_cli`／`windows_service`／`hooks`はすべて`ok: true`
- `hataori mcp status` → `connected: true`、`tool_count: 14`
- Upgrade後も`config/hataori.json`、`data/hataori.db`、`config/hataori.service.json`が保持されていることを確認
- 別途、`hataori.service.json`を削除した状態からの新規Install起動検証: Serviceは正常起動し、`doctor`の`itoguruma`は`degraded`を正しく報告（サーバーログの実際の401エラーと一致）。`service setup`再実行・再起動で`connected`へ復旧することを確認。

## 既知の未解消事項（今回のリリースと無関係）

- `hataori doctor`の`codex_cli`チェックが失敗（`codex`コマンドが本機PATH上に見つからない）。本機にCodex CLIが未導入／未PATH登録という既存の環境要因であり、今回のバージョンアップに起因する退行ではない。

## 未実施

- Uninstall実機検証: `C:\Hataori`が本機の実運用環境（本検証セッションのMCP接続先を含む）であるため、今回もUninstall実機検証を意図的に省略した。次回、実運用に影響しない検証環境で実施する。
