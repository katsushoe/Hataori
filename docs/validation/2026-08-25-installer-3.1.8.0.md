- SHA-256: `C356E5D81C6D287D4195240A4D1EF5C20E75DF696F4CCED35D950AD8F2009410`

- Release構成テスト: 169件合格、失敗0件

- インストール先CLI: 3.1.8.0
- 設定検証: 有効、エラー0件
- Windowsサービス: Running / Automatic
- MCP接続: 接続済み、19ツール
- MCP互換性検証: CodexとClaude Codeで契約Hash・Tool数・`get_version`応答が一致（`compatible: true`）
- Claude Code実クライアントから`claude mcp list`で接続確認（`tools fetch failed`エラーの解消を確認）
- 既知の未解消事項（今回のRelease対象外、実機固有）: `hataori doctor`の`itoguruma`チェックがdegraded、`codex_cli`チェックがCodex実行ファイルパス不整合のため不合格。いずれもHataori側の変更とは無関係の既存環境事象。

## 実装範囲

- `codex_task_started`・`codex_task_release`のMCP Tool戻り値型を`Task<object>`から専用recordへ変更し、outputSchemaが真偽値リテラル`true`になりClaude Code側の厳格なJSON Schema検証で拒否される不具合を修正。
- `ActivationOptions.ProviderPriority`の非空既定値がMicrosoft.Extensions.Configurationのバインダーにより設定ファイルの値へ追記され重複扱いとなる不具合を修正。真に新規のInstallでは`ValidateOnStart`が失敗しWindows Serviceが起動時クラッシュループしていた（Windows Installerエラー1920）。既定値のFallbackは`PostConfigure`／`CliConfigurationManager`／`ProviderPriorityService`側で明示的に適用するよう変更。
- 上記2件の回帰を防ぐ自動テストを追加。

## 実機で発生した事象と対応

移行作業中、旧3.1.7.0（`C:\Program Files\Hataori`）をUninstallした状態で未修正の3.1.8.0が上記Activationバグにより起動クラッシュし、Hataoriが一時的に完全停止した。既知良好なBinary（Git履歴から再構築した3.1.7.0）へ即時ロールバックして復旧した後、原因を特定・修正し、確定Fixで再度Installして最終検証した。
